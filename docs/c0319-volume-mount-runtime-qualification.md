# C-0319 volume mount options qualification

**Disposition: keep C-0319 out of the release bundle.** A Kubernetes v1.37.0 API server with `VolumeBindMountOptions=true` admitted the hardened fixture and preserved `noexec`. Its node rejected that Pod before container creation because the runtime did not advertise mount-option support. Releasing an opt-in policy needs a successful end-to-end run on a runtime that enforces the option. [Rego rule and fixtures](https://github.com/kubescape/regolibrary/tree/b7e57060ca90c41fe15359383245a7c62f09487c/rules/mount-security-options-v1) · [Kubernetes feature design and runtime contract](https://github.com/kubernetes/enhancements/tree/master/keps/sig-node/5855-noexec-emptyDir)

| Test | Result |
| --- | --- |
| Scanner | A candidate CEL expression evaluated with Kubescape's pinned evaluator matched all 23 source fixture verdicts, including the `mountAllowList` override. [Evaluator](https://github.com/kubescape/kubescape/tree/fc41d73e9d5399120283ea19c54af8801546a8e4/core/pkg/opaprocessor/cel) |
| Native admission with the gate enabled | All 23 fixture outcomes matched. The binding rejected a writable mount missing `noexec`, including Deployment, CronJob, init and ephemeral container cases. It admitted explicit and source-level read-only volumes, Windows workloads, the allowlisted path and the hardened Pod. For the ephemeral-container case, create the base Pod and patch its `ephemeralcontainers` subresource with a server dry-run. Kubernetes rejects an ephemeral container in a Pod CREATE before policy evaluation. |
| Native admission with the default-off gate | A separate v1.37.0 API server accepted the hardened Pod dry-run but removed `bindMountOptions` from the returned mount. The same input sent with the gate enabled retained `[noexec, nosuid, nodev]`. [Feature gate default](https://github.com/kubernetes/kubernetes/blob/v1.37.0/pkg/features/kube_features.go#L2273-L2275) |
| Scheduler and kubelet | The official Linux kind v1.37.0 node used containerd v2.3.4. `crictl info` reported no `mount_options` capability on its runtime handlers, and `Node.status.declaredFeatures` lacked `VolumeBindMountOptions`. The scheduled hardened Pod stayed Pending. With `spec.nodeName` set to that node, kubelet marked it Failed with reason `PodFeatureUnsupported`. The disposable test used the node's cached pause image and an emptyDir. [Kind node image](https://github.com/kubernetes-sigs/kind/releases/tag/v0.33.0) · [CRI feature definition](https://github.com/kubernetes/kubernetes/blob/v1.37.0/staging/src/k8s.io/cri-api/pkg/apis/runtime/v1/api.proto) |

To repeat the runtime check, start an isolated Linux cluster with the gate enabled on API server, scheduler and kubelet. Check `kubectl get nodes -o json` for the declared feature and the node's `crictl info` for the runtime-handler capability. Create the upstream `pod-hardened` fixture in a test namespace. A qualifying run must reach a running container and demonstrate that execution of a test binary on its writable mount fails with permission denied. Verify that the same binary runs from a writable control mount without the option. Then repeat the gate-disabled API check and the pinned fixtures before publishing an opt-in artifact.
